the sapphire helper incident_

On 14 October 2026 the helper bot in Sapphire's support server was used to mass-ping everyone. Sapphire says it was not hacked and no user data was accessed. The main bot went offline on purpose while every token was rotated, and everything was back just after midnight.

date 14 oct 2026 times CEST · UTC+2 updated 15 oct, 12:45
  • A flaw in a separate open-source project, Sapphire Images, running on one of Sapphire's servers, let someone read a password file. That file held the token for Sapphire Helper.
  • The person used the token to send @everyone pings in the support server, then messaged the team to explain the issue.
  • Sapphire was not hacked and no user data was accessed, according to its developer.
  • Sapphire and all custom branded bots were shut down on purpose to rotate every token. Everything, including appeal.gg, was fully back by 00:18 on 15 October.

what happened300 pings and a locked server

At about 15:15, Sapphire Helper posted an @everyone message in the Sapphire support server, which has around 72,000 members. It linked to a brand-new server with one member. Some people got the ping around 300 times. Staff deleted the messages and locked text channels while they figured out what was going on.

With chat locked, people moved to voice. One channel passed 100 people before voice got locked too, then opened and locked again several times over the next hour.

the causea side project leaked the token

At 17:16 Sapphire's developer explained it in an announcement to everyone in the server.

the flawSapphire Images, an open-source image host running on a Sapphire server, allowed access to its password file.
the secretThat file contained the Sapphire Helper bot token.
the abuseAnyone holding the token could act as the helper, which only ran in the support server.

"We shut down Sapphire and all custom branded bots as a security measure to rotate all of our tokens, just in case. After we fixed the issue, we confirmed that no user data was accessed."

Sapphire's developer, 17:16

statuswhat we know, and what we don't

confirmed
  • The helper's token came from a password file exposed by Sapphire Images.
  • Sapphire was not hacked and no user data was accessed.
  • The person who found it told the team after using it.
  • The main bot's downtime was a deliberate token rotation.
  • Sapphire, custom branded bots and appeal.gg were fully back by 00:18 on 15 October.
not confirmed yet
  • Exactly how the file could be read. The current Sapphire Images code checks image IDs with a comment saying it's there "to prevent path traversal and glob injection", which may be the fix. Its date isn't confirmed.
  • Which permissions the helper had. Members said Administrator; its own docs ask for much less.

This page doesn't name the person responsible. Plenty of names got thrown around in chat as jokes or guesses, and none are confirmed.

what to dodo you need to do anything?

Probably not. Here's the short version for each case.

you use sapphire

  • Nothing to do. Your server wasn't breached and Sapphire works again.
  • Kicked the bot in a panic? You can add it back now. Settings live on Sapphire's side, so your config should still be there.
  • After re-adding, check the bot's role position. It starts at the bottom.

you're in the support server

  • Don't join the server from the ping. If you did, leave it and don't click any verify links inside.
  • Ignore DMs about the incident that ask you to click something.
  • Bots never see passwords, emails or payment info, so there's nothing to reset.

you run a bot

  • Don't keep tokens where another app on the same machine can read or serve them.
  • Give each service its own user or container and its own secrets.
  • Skip Administrator on helper bots. Grant only what the bot uses.
  • After a leak, rotate every token nearby, like Sapphire did.

contextis this related to double counter?

No. Double Counter, a verification bot, disclosed a separate breach the week before, where an attacker pulled its token from a running server and copied database contents. Sapphire says no user data was accessed here. Both incidents point at the same lesson: whoever can read a bot's token on its server controls the bot.
